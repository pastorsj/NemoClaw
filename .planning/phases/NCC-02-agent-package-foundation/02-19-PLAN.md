# Phase 2 Plan 19: Snapshot and Manifest Authority

<objective>
Bind maintenance backup, rebuild-manifest publication, snapshot restore, and snapshot clone to the
exact harness package recorded for the sandbox.

Purpose: Restore cannot select package authority from a manifest unless backup first records it. A
valid snapshot is not recoverable when its state is interpreted through a newer active package or
checkout definition, and restore validation is too late once a destination is deleted.

Output: Pinned backup inputs, exact versioned manifest identity, restore mutation-edge checks, clone
identity inheritance, and focused failure evidence around stopped containers, Shields, and forced
destination deletion.
</objective>

<threat_model>

- **T-19-01 — Backup definition substitution (critical):** Backup reloads a newer repository or
  active definition. Mitigation: pass and revalidate the pinned definition and identity.
- **T-19-02 — Destructive restore drift (critical):** A target is deleted before package authority
  is known. Mitigation: source/target/object validation before delete and at restore callback.
- **T-19-03 — Clone identity loss (high):** A clone registers only an agent name. Mitigation: inherit
  and publish the source snapshot identity through pending and final records.
- **T-19-04 — Candidate fabrication (high):** Legacy candidate snapshots gain standard identities.
  Mitigation: explicit candidate authority branch and regressions.
- **T-19-05 — Manifest downgrade (critical):** Package identity is omitted, normalized away, or
  replaced with owner-only migration audit data. Mitigation: versioned exact identity schema and
  distinct legacy, candidate, malformed, and package-managed states.

</threat_model>
